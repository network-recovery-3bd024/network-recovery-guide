<a id="scope"></a>
## 先确认是全设备还是单个应用失败

选择一个不需要代理的普通小页面，分别在原浏览器和另一个已有应用中观察。记录是只有浏览器报代理连接失败、多个程序都失败，还是只有某个域名找不到。不要安装新工具来扩大排查面。

查看系统是否连接到预期网络，是否存在待完成的 Wi-Fi 门户登录；必要时使用自己的已知正常网络做一次对照。另一个网络正常而原网络失败时，保留这个差异，先查接入端，不删除系统网络组件。

比较时不访问需要特定代理路径或隐私保护的内容。测试普通直连本身会改变访问路径，应限定在这类无敏感内容的小任务内。

<a id="exit"></a>
## 客户端还能打开时先正常退出

重新打开原软件，查看它是否仍负责系统代理、TUN 或 VPN 会话。按软件自己的正常功能关闭本次启用的接管，再退出。直接结束进程不一定会恢复所有设置，所以先利用软件支持的退出流程。

退出后再次验证基础小页面。如果恢复，记录有效步骤；下次调整接管方式前留下原设置，不把每次强制结束进程当成正常退出方法。

若客户端无法启动，不为恢复联网立即导入陌生“修复配置”。先保存错误，进入下列归属核查；不知道某个设置由谁管理时就停止改动。

<a id="proxy"></a>
## 检查系统和应用各自的代理

在系统官方提供的代理设置界面查看是否仍指向本地地址与端口。只有确认它由刚才的软件创建、且已有原值记录时，才恢复到此前状态。地址为本机并不代表必然可以删除，其他合法软件也可能使用本地代理。

随后查看失败应用是否单独配置了代理或自动配置脚本。系统代理恢复了，应用自己的设置仍可能保持旧值；反过来也一样。逐项恢复，每改一项复测，不同时清空所有设置。

自动代理脚本、企业 VPN 或系统管理配置可能由组织下发，不擅自删除。发现“由组织管理”或设置归属不明时，向管理员报告发生时间和改动经过。

如果只有终端内的程序失败，核对该程序官方文档说明的代理来源。不要复制包含密钥的环境输出到公开聊天，也不要用陌生命令批量清除全部环境变量。

## DNS 错误与证书错误不要混为一谈

“无法找到主机”可以作为解析方向的线索，但代理未连通也可能让请求在其他阶段失败。先看具体错误，不一上来把浏览器、系统和客户端的 DNS 同时替换。

若曾手动修改 DNS，按事前记录恢复那一层设置，再测相同页面。没有记录且处于受管理网络时，交由管理员确认；不要随意填写网上声称最快的地址。客户端负责解析时，其配置与系统配置也不能简单视为同一处。

遇到证书异常时停止访问并核对设备时间、目标域名和真实软件来源。不能通过关闭证书校验、安装来历不明根证书或绕过浏览器警告把它当作“网络恢复”。错误持续时把脱敏提示交给对应支持方。

## 仍不恢复时如何停止扩大改动

已经恢复明确属于本次操作的设置，基础网络仍失败，就保存当前结果，不继续删除网卡、重置全部网络或关闭防火墙。这些改动可能影响其他正常连接，也会破坏现有排障线索。

反馈用时间线描述：原网络正常 → 启用何种接管 → 如何退出 → 哪些应用报什么错 → 已恢复哪些已知设置 → 一次网络对照结果。日志中隐藏账户令牌、完整订阅、私人目标和网络密码。

恢复成功后，再按自己的需求重新启用代理并验证原业务，然后正常断开复测基础网络。两种状态都能按预期工作，才算完成，不把另一台设备能联网算作本机已修复。

技术背景可参考 [Mihomo DNS 配置](https://wiki.metacubex.one/config/dns/)；本文并不要求普通用户手工编辑这些参数。2026-11-26 首次整理，系统菜单与恢复流程以实际系统和软件当前说明为准。
